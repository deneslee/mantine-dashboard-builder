## 1. Question and scope

Where should code live inside the future `apps/web/src`, and what moves to `packages/`? Six questions from the brief:

1. What bulletproof-react actually does today.
2. How TanStack Router/Start projects keep route files thin.
3. Concern subfolders vs file-kind subfolders vs a hybrid inside a feature.
4. Folder and file naming, and concrete names for the 01 §1.3 collisions.
5. Where app composition, shell, the design system and cross-cutting services go in `apps/` vs `packages/`.
6. Two concrete `apps/web/src` trees with a move map and a feature template.

Out of scope: the plugin model itself (G-002, D2/D3), the task runner (Q12) and test/lint cuts (U8/U9). Where this topic touches them, it says so and leaves the decision to that topic.

User constraints that apply: D6 (feature folders with `components/` and `hooks/`, no ambiguous same-name folders, no flat grab-bags; a direction to recheck, not a decision), §3.1 Q1 (monorepo-style `apps/` + `packages/`, unpublished), D2 (plugins stay folders, no package per plugin), D5 (staged, behaviour kept), and the guidance not to use Mantine's repos as a reference.

## 4. Implications for this repo

1. **The no-cross-feature rule decides where the two `app/` glue files go (G-008).**
   - `app/recordSync.ts` (RP-3) imports only dashboards and `lib/records`, so it can move into `features/dashboards` as a start function that bootstrap calls.
   - `app/storageCollections.ts` (RP-4) imports two features. Moving it into either one creates a cross-feature import, which BP-6 and today's lint both forbid. It stays in `app/`, in a named composition folder.
   - So G-008's "move domain glue to its feature" holds for `recordSync` only.
2. **Splitting `features/datasources` into several features would create cross-feature imports** (RP-5). `DatasourcesPage` renders `PluginsSection` and `VaultStatus`, and `PluginsSection` reads `useConnections`. The split that keeps 01 §1.8 ("no feature-to-feature imports") true is one feature with UI areas, renamed for what it owns (connections). The vault **service** is already shared (`lib/vault`). The vault **dialogs** have one consumer, so they stay in the feature until a second consumer appears.
3. **`dashboards` is the only feature that needs areas** (RP-1/RP-2). Every other feature fits B with 1–2 folders, as in bulletproof (BP-3).
4. **Query options belong in the feature's `api/`, next to their hooks** (BP-4, TS-6, TS-10). Today `features/dashboards/data/dashboardQueries.ts` already is that file. Lint rule `app/no-datasource-query` keys on its path (01 §1.7), so its new path must be set in the same commit (G-019).
5. **Route files can drop to "wire only"** (RP-6). `DashboardRouteData`, the draft check and the loader body move to `features/dashboards/api/`. The route keeps `validateSearch`, `beforeLoad` and `loader` as one-line calls, which stay in the critical chunk (TS-5). Its `@/app/plugins` import is legitimate: routes are the app layer.
6. **Using TanStack defaults (`src/routes`, `src/routeTree.gen.ts`) removes two overrides** (TS-3, G-019). Today they are `src/app/routes` and `src/app/routeTree.gen.ts`.
7. **Packages cannot use `@/*`** (TR-2). Every file that moves into `packages/*` changes its imports, from `@/core/...` to `@scope/core/...` or relative/`#` imports. Inside `apps/web`, `@/*` can stay. Package edges (pnpm only links a package's declared dependencies) replace the cross-layer `layer()` globs, and the `barrels` globs (RP-8) shrink to the app's internal layers. **They do not stop relative imports that climb out of a package root** (`../../src/core` is exactly G-012). One rule against that is still needed. 01 lists the lint-enforced graph as a strength to preserve, so this is a re-keying, not a removal.
8. **Naming and Windows** (NM-3). Full kebab-case for files would rename all 185 PascalCase files in `src/`. 33 of them are single-word names (`Shell.tsx`, `Panel.module.css`, …), and on the user's OS those are case-only renames. Kebab-case **folders** are cheap, because almost every folder moves anyway, and they are required for package folders (NM-1).
9. **`apps/docs` cannot stay under `apps/`** if `apps/` means applications (TR-1, G-033). The relay becomes `apps/relay`, and `core/relay` becomes a contract package (G-012, G-021).

## 5. Recommendation

All of this section is **[R]**. It assumes D6 and Q1 as answered, and the plugin-model topic owns final names for the plugin contracts (G-002).

### 5.1 The rule for features (Q3)

1. **File kind first.** A feature may have `api/`, `components/`, `hooks/`, `stores/`, `utils/`, `types/`, and creates only the ones it needs (BP-1, BP-3).
   - `api/` — query options, query and mutation hooks, fetchers, loader helpers. **Hooks that use TanStack Query go here, not in `hooks/`** (BP-4).
   - `hooks/` — hooks that do not fetch: UI state, effects, store selectors.
   - `stores/` — Zustand stores and their React provider.
   - `utils/` — pure functions with no React.
   - `types/` — only when a type is shared by more than one kind folder. Otherwise keep it in the file that owns it.
2. **Areas only inside `components/`, and only past ~12 files.** Name an area for a part of the screen the user can point at (`grid`, `editor`, `toolbar`, `inspect`). Page components sit at the `components/` root.
3. **No logic in an area folder that is not UI.** File I/O, formatting and parsing go to `utils/` (this fixes `header/` mixing, 01 §1.3).
4. **Max depth 4 under `features/`** (RE-1).
5. **Tests and stories sit next to the file** (keeps today's practice; no `__tests__/` folders).
6. **Cross-feature composition happens only in `routes/` or `app/compose/`** (BP-5, BP-6). Keep the existing lint mechanism, re-keyed.

### 5.2 Routes (Q2)

- `apps/web/src/routes/` at the TanStack default path, with the generated tree at `src/routeTree.gen.ts` (TS-3).
- A route file holds `createFileRoute`, `validateSearch`, `beforeLoad` and `loader` calls into a feature's `api/`, `staticData`, and a component that renders a feature page. Do not export route properties (TS-5).
- `-` folders only for route-private files that no feature owns (today: `-PlaceholderPage.tsx`, loader tests). Pathless `_layout` only when a guard arrives (G-004). No route groups until there is a grouping need.

### 5.6 Feature template

```
features/<feature-name>/            # kebab-case, a noun the user would name
  api/                              # data: query options, query/mutation hooks, fetchers, loader helpers
    <thing>Queries.ts               #   queryOptions + key factory + useXQuery hooks (BP-4, TS-10)
    <thing>Api.ts                   #   calls to providers or plugins; no React
  components/                       # UI only
    <Feature>Page.tsx               #   the page a route renders
    <area>/                         #   only once components/ passes ~12 files
      <Component>.tsx  <Component>.module.css  <Component>.test.tsx  <Component>.stories.tsx
  hooks/                            # non-fetching hooks: useX.ts
  stores/                           # create<Thing>Store.ts, <Thing>Provider.tsx
  utils/                            # pure functions, no React; node-environment tests
  types/                            # only for types shared across the folders above
```

Rules: create only the folders you need. No `index.ts`. Relative imports inside the feature, `@/…` or package names outside it. No imports from other features, `app/` or `routes/`.
